# Phase 1.3 — Prefect 3.x Integration (Approach A+)

> Design spec. Brainstormed and self-reviewed 2026-05-03. Approved by Louis.
> Implementation plan: [docs/superpowers/plans/2026-05-03-phase-1.3-prefect-integration.md](../plans/2026-05-03-phase-1.3-prefect-integration.md).

## Context

The AI Orchestrator (currently at `v0.1.2-phase1.2`) is a generic, autonomous-agent
platform that already routes LLMs, runs sandboxed code, maintains a 5-layer memory
system, runs parameter-sweep campaigns (Phase 1.1), and emits citation-grade
evidence bundles (Phase 1.2). Today, agent runs are spawned by the FastAPI process
as `threading.Thread(daemon=True)` workers; per-run state lives in the in-memory
`RUN_STATUS` / `CAMPAIGN_STATUS` dicts; there is no persistent flow-run history,
no native retry/backoff on transient Ollama errors, and no resume-after-crash.

Phase 1.3 introduces Prefect 3.x as the workflow engine. The user's framing is
**"future-proofing, not solving current pain"**: the goal is to install hooks
that downstream phases (1.4 DVC, 1.6 Python client, 2.5 SkyPilot cloud-burst,
2.6 new UI) can attach to, without rewriting code that already works.

A secondary goal — folded into this phase to avoid scope thrash later — is the
deferred Phase 1.2.x item: **per-LLM-call telemetry capture into the evidence
bundle's `LlmCall[]` array**. With per-LLM-call Prefect tasks, this becomes
automatic from task state hooks rather than a separate effort.

## Goals

1. Wrap `run_orchestration` and `run_campaign` as Prefect flows; agent functions
   and Ollama calls become Prefect tasks.
2. Two execution modes (config switch, default `in_process`):
   - **`in_process`** — FastAPI spawns a daemon thread that invokes the flow
     callable (`run_orchestration(req, run_id)` — NOT `.fn()`, which would
     bypass Prefect tracking). Prefect server still tracks state via its
     API client.
   - **`deployment`** — FastAPI submits flow runs to Prefect's work pool;
     a `prefect-worker.service` systemd unit on the orchestrator LXC executes them.
3. RUN_STATUS / CAMPAIGN_STATUS dicts are kept and continue to drive the existing
   WebSocket `/ws` UI. Populated by **both** Prefect state hooks (primary path)
   **and** the existing inline `_update_run_status()` calls (kept as
   belt-and-suspenders so the server-down fallback path — which uses
   `run_orchestration.fn(...)` and bypasses Prefect entirely — still produces
   live UI updates). Hooks are idempotent over inline calls; no loss of
   correctness from the duplication.
4. Capture per-LLM-call telemetry into `LlmCall[]` records emitted into the
   Phase 1.2 evidence bundle (closes deferred Phase 1.2.x item).
5. Free wins: per-LLM-call retries with exponential backoff; flow-level
   resume-after-crash for individual runs; cancellation always emits an
   evidence bundle (today's abort path doesn't).

## Non-goals (deferred to later phases)

- Replacing RUN_STATUS / CAMPAIGN_STATUS dicts with Prefect events as the
  WebSocket source of truth — Phase 2.1 (Postgres) or 2.6 (new UI).
- Migrating dict state to Postgres — Phase 2.1.
- Postgres backend for the Prefect server itself — SQLite is sufficient until
  Phase 2.1; swap is one config line.
- Distributing workers to remote LXCs / SkyPilot — Phase 2.5; `deployment` mode
  is the hook for this, but no remote workers ship in 1.3.
- Memory layer / vault writes running concurrently — kept sequential to preserve
  any unspecified ordering dependencies.

## Architecture

```
┌────────────────────────────┐         ┌──────────────────────────────────┐
│ NEW LXC: prefect-server    │         │ EXISTING: ai-orchestrator        │
│ (Tailnet hostname TBD)     │         │ (192.168.2.218)                  │
│                            │         │                                  │
│  prefect server start      │◀───────▶│  FastAPI (uvicorn :8000)         │
│  - SQLite (Postgres in 2.1)│  HTTP  │   ├─ api/routes.py                │
│  - UI :4200 (Tailnet only) │  4200  │   ├─ orchestration/   (@flow)     │
│                            │         │   ├─ llm/ollama.py    (@task)    │
│                            │         │   └─ prefect_io/      (NEW)      │
│                            │         │                                  │
│                            │         │  prefect-worker.service          │
│                            │         │   (only when execution_mode=     │
│                            │         │    "deployment")                 │
└────────────────────────────┘         └──────────────────────────────────┘
                                                    │
                                                    ├─→ memory layers (disk)
                                                    ├─→ vault → NoteDiscovery
                                                    └─→ evidence bundles
```

**Trust boundary:** Prefect server is on the Tailnet only; `PREFECT_API_URL`
points at its Tailscale hostname. No public exposure.

**Failure modes:**
- Prefect server down → `prefect_io.submit_*` falls back to today's daemon-thread
  spawn. WARNING logged, Gotify notification fired.
- Worker process crash (deployment mode) → flow runs queue; in-flight run gets
  retried on worker restart per Prefect's native semantics.

## Data flow

### Per-run path (in_process mode)

```
1. POST /orchestrate                                api/routes.py:162
       │
       ▼
2. prefect_io.submit_orchestration(req, run_id)     prefect_io/__init__.py
       │  - registers flow_run_id with Prefect server (sync API client call)
       │  - spawns daemon thread that calls the flow callable:
       │       threading.Thread(target=run_orchestration, args=(req, run_id),
       │                        daemon=True).start()
       │    (calling run_orchestration() — NOT .fn() — keeps Prefect's state
       │     tracking, hooks, and retries active)
       │  - returns {run_id, flow_run_id} immediately
       │
       ▼
3. @flow run_orchestration                          orchestration/__init__.py:983
       │
       │   planner_agent.submit()                   @task
       │   ├─ query_ollama_structured.submit()      @task tags={"llm-call"} retries=3
       │   │
       │   generate_candidate.map(models=[...])     @task (parallel via Prefect)
       │   judge_score.submit()                     @task
       │   optimizer_agent.submit()                  @task
       │   troubleshoot.submit() (if needed)         @task
       │
       │   Post-run (sequential):
       │     update_memory()        @task
       │     update_negative_memory @task
       │     rewrite_primer()       @task
       │     record_session()       @task
       │     hindsight_retain()     @task
       │     vault_after_run()      @task
       │     consolidate_lessons()  @task
       │     _safe_emit_evidence()  @task
       │
       ▼
4. State hooks fire on every transition             prefect_io/state_hooks.py
       ├─→ RUN_STATUS[run_id] mutated → _ws_broadcast (UI updates)
       └─→ LlmCallLogger.append(LlmCall(rendered_messages, sampling, response_tokens, duration_ms))

5. Flow completion → on_completion hook
       ├─→ evidence builder drains LlmCall log into bundle
       └─→ run terminal state visible in Prefect UI + RUN_STATUS
```

### Per-campaign path (deployment mode)

Identical flow body. Step 2 swaps `daemon thread` for `await prefect_client.run_deployment(name="orchestrate", parameters=...)`. The worker process pulls from the work pool and runs the flow. Pause/resume/abort hit Prefect's flow-run state API.

### Cancellation path (new)

User aborts → `POST /campaigns/{id}/abort` → `prefect_io.cancel_flow_run(...)` → Prefect propagates `CancelledError` at next task boundary → `on_cancelled` hook fires → `_safe_emit_evidence(campaign_id)` runs. Today's abort path does not emit evidence; this is a new behavior.

### Server-down fallback

`prefect_io.submit_*` calls `prefect_client.healthcheck()` with a 5s timeout. On failure: WARNING logged, Gotify fired, falls back to `threading.Thread(target=run_orchestration.fn, args=(req, run_id), daemon=True).start()` — note `.fn` is intentional in the fallback path: with no Prefect server reachable there is no state to track, and `.fn` invokes the underlying Python function directly without attempting to register a flow run. RUN_STATUS / WebSocket still work via the existing inline status updates that we leave behind on the `.fn` codepath. No Prefect UI visibility for fallback runs.

## Error handling

Three layers, each with explicit semantics:

**Layer 1 — Per-LLM-call (`@task(retries=3, retry_delay_seconds=[1,5,15])` in llm/ollama.py)**

- Network errors / Ollama 5xx / timeouts → exponential backoff retry.
- Exhausted retries → task fails. Caller decides:
  - Planner → flow fails fast.
  - Generate-candidate → that candidate is dropped from the `.map()` result; flow continues if any other generator succeeded.
  - Judge → existing fallback-model logic still runs (documented as "Prefect retries primary judge first, then JUDGE_FALLBACK_MODEL on a fresh task call").
  - Optimizer/troubleshoot → flow continues with last-good state.
- Internal JSON-repair retries inside `query_ollama_structured` stay (different concern: bad LLM output, not network).

**Layer 2 — Per-flow-task**

- Agent functions (planner, judge, generate, optimizer, troubleshoot): `@task(retries=0)` — they orchestrate LLM calls; the LLM call task already has retries.
- Memory / vault / evidence post-run tasks: `@task(retries=2)` for transient I/O failures (disk full, NAS unmount). Permanent failures recorded in Prefect state but don't fail the flow (preserves today's swallow-and-continue).

**Layer 3 — Per-flow-run (`@flow(retries=1, retry_delay_seconds=60)` on run_orchestration)**

- Whole-flow retry on uncaught exception or hard process crash mid-flow. One retry, 60s delay.
- Idempotency: re-doing already-completed tasks is safe — memory writes are content-addressed, vault overwrites, evidence builder is idempotent.
- Campaign-level: `@flow(retries=0)` on `run_campaign` — campaigns are long; whole-campaign restart is undesirable.
